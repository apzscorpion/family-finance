## 3. Why things were not working

This section is the useful part. Each is a real root cause, not a guess.

### 3.1 Five source files were silently empty

`calc_engine.dart`, `recurring_sheet_v3.dart`, `calc_engine_test.dart`,
`v3_actions_test.dart` and `20261006230000_recurring_income_support.sql` were all
**0 bytes** in the working tree while intact in commit `8333a72`. They showed as
`M` in `git status`, which reads like work in progress rather than data loss.

This produced five analyzer errors and made the app unbuildable. Restored with
`git checkout HEAD -- <paths>`.

The migration is the dangerous one — see §1.2. A migration that is pushed while
empty is recorded as applied forever.

### 3.2 Recurring salary credited to the wrong person

`post_due_recurring()` inserted the generated transaction as:

```sql
values (r.family_id, auth.uid(), auth.uid(), ...)
```

`auth.uid()` is **whoever happened to open the app and trigger the posting**, not
the person the charge belongs to. And `recurring_charges` had no owner column at
all, so there was nothing to attribute against.

Effect: a salary set up by one person was credited to whichever family member
opened the app that day.

Fix (`20261007090000_recurring_owner.sql`):

- `recurring_charges.owner_user_id` added, set to the creator on insert
  (`V3Repository.addRecurring` defaults it to `currentUserId`).
- `post_due_recurring()` now uses `coalesce(r.owner_user_id, auth.uid())` for
  both `user_id` and `paid_by`.
- Backfill only fills families with exactly **one** active member, where the
  owner is unambiguous. Multi-member families are left `null` deliberately —
  guessing would silently move someone's salary onto the wrong person.

**Consequence that still needs work:** existing recurring rows in a multi-member
family remain `null` and keep the old fallback until re-saved. There is no owner
picker in the recurring sheet yet. See §5.1 — this is the highest-value next task.

### 3.3 CSV import filed income as spending

Two faults compounding. The first was the real one.

**Fault A — the column matcher.** `_matchColumn` fell back to a plain substring
test:

```dart
if (header[i].contains(k)) return i;     // k is from ['credit','deposit','cr',...]
```

`"description"` contains `"cr"`. So on **any** CSV with a Description column the
credit column bound to the description. The debit/credit branch then ran against
a column holding text rather than money, found no amount, and — critically —
skipped all direction inference. The same trap applies to `"dr"`.

This is why nothing about income ever worked: almost every real CSV has a
Description, Narration or Particulars column.

Fixed with whole-word matching (`_headerMentions`).

**Fault B — direction inference.** Even once reached, inference only consulted a
`type` column. A row categorised `Salary` with no type column imported as a spend.

Direction is now resolved in order of how trustworthy the signal is:

1. explicit debit / credit columns
2. a `type` column
3. the sign of the amount, **only if the file actually uses signs** — decided
   across the whole file, because an export where every amount is positive is not
   signed, it is just all spending
4. the category, then the description

**Fault C.** `_parsePositional` had `isIncome: amount > 0 && false`, which is
never true. Every headerless row imported as a spend regardless of its text.

Income words are matched on word boundaries, so `"creditors"` is no longer
credit. `"Loan"` is treated as money borrowed unless the text also mentions an
EMI, repayment, interest or payment, since the word covers both directions.

Covered by 16 tests in `test/expense_import_income_test.dart`.

**Caveat:** fixed against the described symptoms, not against the actual file —
the CSV was never shared. Re-import to confirm.

### 3.4 Family scope

`V3State.scope` defaulted to `'family'`, so the app opened on the household view
and every personal total read as everyone else's.

Now: the Family chip is gone from the home scope strip, and scope defaults to the
signed-in member once the workspace loads. A `_scopeChosen` flag stops a later
refresh overwriting a deliberate switch.

The household view is still reachable from the "View finances for" sheet and the
Family tab — deliberately kept, per the decision taken in session.

Note: `home_v3.dart` still has `if (s.isFamily && s.byMember.isNotEmpty)` around
the "Who spent" block. That is now rarely true. Either leave it (harmless) or
move the block to the Family tab.

## 4. What was built

### 4.1 Prayer times (items 1–3)

```
lib/v3/data/prayer/
  prayer_cities.dart      ~250 bundled city coordinates, India/Gulf weighted
  prayer_config.dart      device-local config + PrayerSlot/Method/Madhab
  prayer_service.dart     pure calculation, PrayerDay / NextPrayer / HijriDate
  prayer_notifier.dart    rolling 7-day notification window
  prayer_location.dart    one-shot coarse GPS
  prayer_controller.dart  ChangeNotifier, minute-aligned timer, lifecycle
lib/v3/widgets/prayer_ring.dart    countdown ring + day rail (CustomPainter)
lib/v3/widgets/prayer_card.dart    home card
lib/v3/screens/prayer_v3.dart          full page
lib/v3/screens/prayer_settings_v3.dart settings
```

Key decisions:

- **`adhan` package**, pure Dart. No API key, no network, works offline.
- **Config is device-local** (SharedPreferences), *not* `user_preferences`. That
  table is family-scoped, so a toggle there would push one member's Fajr alert
  onto every other member's phone.
- **City picker is the default** location path and needs no permission at all.
  "Use my location" takes a single coarse fix. `ACCESS_FINE_LOCATION` is stripped
  from the merged manifest.
- **Hijri date is tabular/arithmetic**, which can sit a day off a sighting-based
  calendar. There is a `hijriOffset` setting (−2..+2) and the UI says "approx."
  rather than claiming authority.
- **Exact alarms are opt-in.** Default is `inexactAllowWhileIdle`, because exact
  alarms are the single biggest battery lever here.

44 tests: `test/prayer_service_test.dart`, `test/prayer_widgets_test.dart`.

### 4.2 Shared notification core

`lib/v3/data/notifications_core.dart` — `AppNotifications`.

`FlutterLocalNotificationsPlugin` is a **singleton**, so whichever caller ran
`initialize` last silently won, taking the response callbacks with it. Reminders,
prayer alerts and the future live card now share one initialised instance.

Reserved id ranges: cards `100000`, recurring `200000`, prayer `300000`, live
`400001`.

The plugin's boot and action receivers are now declared in the manifest. Without
the boot receiver **every scheduled alert was lost on restart** — this was already
true for the existing reminder code.

`ReminderService` was refactored onto this core. Note it is **dead code**: defined
but never called from anywhere. It was dead before this work too. Either wire it
up or delete it.

### 4.3 Notes paste structuring

`lib/v3/data/note_structure.dart` — `NoteStructure`.

The headline behaviour: a run of bare lines becomes **one checkbox per line**.

```
Milk              →   ☐ Milk
Eggs                  ☐ Eggs
Bread                 ☐ Bread
```

Previously that produced a single paragraph; the old parser only recognised lines
that already carried a bullet, number or checkbox.

Prose still has to survive, so a run only becomes a checklist when its lines look
like items: at least two, each ≤ 90 chars, and most not ending in sentence
punctuation.

Tables are inferred only from genuinely delimited data (pipes, tabs, CSV with ≥3
fields). Content that merely *could* be tabular — `Day 1: Tokyo` — becomes a
checklist, because guessing wrongly towards a table is far more annoying to undo.
`NoteStructure.toTable()` converts in one step, splitting on whichever separator
every item shares. `toTodo()` and `toParagraph()` go the other ways.

32 tests: `test/note_structure_test.dart`.

### 4.4 AI provider layer

```
lib/v3/data/ai/ai_config.dart      provider, key, model, base URL; device-local
lib/v3/data/ai/ai_structurer.dart  the call + strict parsing
```

Providers: **Gemini** (default, `gemini-2.5-flash`), **Claude**
(`claude-opus-5-5`), **OpenAI** (`gpt-4o-mini`), and **any OpenAI-compatible
endpoint** — OpenRouter, Groq, a local Ollama — which is what makes "configure
whatever you like" true.

- The key is the **user's own**, stored on the device. No key in the APK, nothing
  proxied through our server. It is not synced to Supabase: an API key is personal
  and billed to one person.
- Gemini and Claude constrain the reply with a native response schema. The
  OpenAI-compatible path uses plain `json_object`, because strict `json_schema`
  support is patchy across the endpoints people actually use. Gemini rejects
  `additionalProperties`, so it gets a permissive variant of the same schema.
- **Model output is treated as data.** The reply is parsed into a fixed block
  shape and anything unrecognised is dropped. The prompt also tells the model to
  structure any instructions it finds in the pasted text rather than follow them.

Not yet reachable from the UI — see §5.3.

## 6. Constraints to honour

### 6.1 The lightweight requirement is a real constraint

It was stated explicitly and it drove the prayer design. Keep to it:

- **No background service, no WorkManager, no foreground service.** Prayer
  scheduling is a rolling window refreshed on resume. Idle cost: zero.
- **No per-frame animation.** The countdown ring ticks once per minute via a
  single `Timer`, cancelled in `dispose` and when the app backgrounds. The
  painters' `shouldRepaint` compares at minute resolution.
- **Disabled features build nothing.** `PrayerCard` returns
  `SizedBox.shrink()` and registers no timer when off — it is not a hidden
  `Visibility`.
- APK grew 55.3 → 57.9 MiB (+2.5 MiB) for four plugins. Report the number when
  it moves.

### 6.2 Privacy posture

Prayer config, AI keys and the quick-add queue are all device-local. Prayer times
are computed on-device; no location leaves the phone. OCR is on-device. Keep new
features to this standard, and say so in the UI where a user would reasonably
wonder.

### 6.3 Sideloading and Play Protect

`android/app/build.gradle.kts` has a long comment explaining it: Google's
sideload protection refuses to install an APK declaring
`BIND_NOTIFICATION_LISTENER_SERVICE` from a browser or file manager. That is why
the listener lives only in the `detect` flavour.

**Do not move it into the main manifest.** The main manifest also actively strips
`REQUEST_INSTALL_PACKAGES`, `READ/WRITE_EXTERNAL_STORAGE`, `READ/RECEIVE_SMS`,
`ACCESS_FINE_LOCATION` and `CAMERA` with `tools:node="remove"`. Keep that list
tight; each addition is a sideload risk.

### 6.4 NDK

Bumped to `28.2.13676358` because the new plugins require it. Leave it.

## 7. Traps found along the way

### 7.1 v1.9.0 crashed on launch — release-only, and how it got through

The shipped v1.9.0 died before any Dart ran:

```
java.lang.RuntimeException: Unable to get provider
    com.google.mlkit.common.internal.MlKitInitProvider
Caused by: Unsatisfied dependency for component
    com.google.mlkit.vision.text.internal.zzo
W/ComponentDiscovery: NoSuchMethodException: CommonComponentRegistrar.<init> []
```

ML Kit discovers its components reflectively from a `ContentProvider` that
Android installs during application bind, **before the Flutter engine starts**.
R8 removed the no-arg constructors those registrars are instantiated through, so
the provider threw and took the process with it. The keep rules shipped with the
dependency covered `com.google.mlkit.vision.text.**` but not `common.internal.**`
or the registrars.

**Why it was not caught:** R8 does not run on debug builds. The debug build
passed, 165 tests passed, and the release APK was *built* — the output said
`√ Built app-standard-release.apk` — but never *installed and launched*. A green
release build says nothing about whether the app starts.

**The standing rule this produces:** before publishing an APK, install it on a
device or emulator and launch it.

```bash
adb install -r mobile/build/app/outputs/flutter-apk/app-standard-release.apk
adb logcat -c && adb shell am start -n com.familyfinance.family_finance/.MainActivity
sleep 12 && adb logcat -d | grep -E "FATAL EXCEPTION" ; adb shell pidof com.familyfinance.family_finance
```

A live pid and no `FATAL EXCEPTION` is the minimum bar. This is cheap and would
have caught it in under a minute.

Secondary lesson: the dependency was added **ahead of the feature that needed
it**, so it delivered nothing while carrying all the risk. Add native
dependencies in the same change as the code that uses them.

### 7.2 Other traps

Worth knowing before repeating them.

| Trap | What happens |
|---|---|
| **Bash heredocs mangle backslashes** in this environment, even quoted (`<<'PY'`). `\b` in a regex became a literal backspace byte (`0x08`) in the Dart source and the pattern silently stopped matching. | Write regex/escape-heavy code with the editor tools or a script file, never a heredoc. Verify with `cat -A`. |
| **`testWidgets` runs in a fake-async zone.** Awaiting real platform-channel work inside it hangs forever with no output. | Wrap setup in `tester.runAsync`. Cost us a 10-minute silent hang. |
| **`ListView` builds lazily.** A widget below the fold does not exist, so `find.text` returns nothing and the test looks like a bug. | `tester.scrollUntilVisible` first. |
| **`FlutterLocalNotificationsPlugin` is a singleton.** The last `initialize` wins and takes the callbacks. | Everything goes through `AppNotifications`. |
| **Substring column matching.** `"description".contains("cr")` — see §3.3. | Match header keys as whole words. |
| **A 0-byte migration can be recorded as applied.** | §1.2. |
